# BAYT Admin Portal

Swedish property management (BRF) SaaS. Admin-only in v1. Standalone Vite SPA (converted off Lovable) — GitHub Pages via Actions, Supabase backend. All UI text is Swedish.

## Stack
- Vite + React 19 + TanStack Router (file-based routing) + TanStack Query
- Supabase (Postgres, Auth, Storage, Edge Functions) — client at `src/lib/supabase.ts`
- Tailwind v4 present but most pages use inline `style={{}}` objects with a local `const C = {...}` color palette per file (not a shared theme file)
- Fonts: Outfit (headings) / Inter (body), loaded via Google Fonts in `index.html`
- No SSR — pure client-side SPA. `ssr: false` on some routes is a harmless leftover from the pre-conversion codebase.

## Routing convention
File-based, dots = slashes: `_authenticated.properties.$id.issues.$issueId.tsx` → `/properties/:id/issues/:issueId`.
`_authenticated.tsx` is the layout route (auth guard + `AppShell`). Routes under it require `role = 'admin'` in `profiles`, enforced in `beforeLoad`.
Public routes (no auth): `login`, `start`, `demo`, `felanmalan`, `boende`, `styrelse`, `index`.
Global list/detail routes (`/issues`, `/inspections`, `/projects`) and property-scoped versions (`/properties/:id/issues`) often share the same component — check for a thin wrapper route importing the page component with an `initialPropertyId` prop before assuming duplication.

## Data model essentials (Supabase, public schema)
Core tables: `properties`, `apartments`, `issues` (felanmälningar), `inspections` (besiktningar), `projects`, `contacts`, `documents`, `logbook_entries`, `property_objects`, `profiles`.

- **Ärende lifecycle** (issues/inspections/projects): `vilande` (dormant/new) → `oppet` (active) → `avslutat` (closed). Issues use the `status` column (`issue_status` enum: ny/pagande/vantar/klar/fakturerad/stangd — mapped to the 3-stage lifecycle via `LIFECYCLE_OF` in `src/lib/issue-tokens.ts`). Inspections/projects use a plain `arende_status` TEXT column with literal `vilande/oppet/avslutat` values. The shared `<OppnaArendeButton>` / `<AvslutaArendeButton>` components flip vilande→oppet and oppet→avslutat, each rendering only in its valid stage. **Exception: `<AvslutaArendeButton allowVilande>`** also renders on a vilande ärende and writes the same close transition straight from vilande (loggboken reads `vilande → avslutat`). It keeps the label **"Avsluta ärende"** — deliberately not a second name for the same action. It is opt-in and only Dag Rapport's entreprenörssheet passes it — the three detail pages keep the strict ladder. **These two buttons are the only writers of an issue's `status` column** — they also insert the `issue_status_history` row. Everything else treats `status` as read-only.
- **Ärendestatus is derived, never chosen — for all three ärendetyper.** No status dropdown exists on felanmälan, besiktning or projekt. `src/lib/issue-tokens.ts` holds one shared rule engine (`deriveFromDue`) and three entry points, all returning the same `DerivedStatus` (`Ny | Pågående | Brådskande | Försenad | Avslutad`, + `Pausad | Avbruten` for projekt) plus a Swedish `reason` string:
  - `deriveIssueStatus` — explicit `deadline` wins; with none, `SLA_DAYS[priority]` (akut 1, hög 2, normal 5, låg ingen) from `created_at`.
  - `deriveInspectionStatus` — `next_due_date` wins; with none, `last_completed_date + interval_months` (month-clamped: Jan 31 + 1 mån = Feb 28).
  - `deriveProjectStatus` — `end_date`; `pausad`/`avbruten` short-circuit the dates.
  - Shared rule: overdue → Försenad, ≤1 dygn left → Brådskande, else lifecycle decides Ny vs Pågående; `avslutat` short-circuits everything. Rows predating `arende_status` fall back to the legacy `status` column (`klar`/`avbruten` = closed, else öppet).
  - Render through `<DerivedStatusBadge>` / `<DerivedStatusField>` (`src/components/DerivedStatusBadge.tsx`) — never a local badge map. Surfaces already wired: all three detail pages, `IssuesTab`/`InspectionsTab`/`ProjectsTab`, the apartment felanmälan + besiktning tables, the apartment Tidslinje meta, the objekt besiktning list, and dag-rapport. Add a new one the same way or the app will contradict itself.
  - **Writers of a status column, exhaustively:** `OppnaArendeButton`/`AvslutaArendeButton` (lifecycle) and `ProjektStatusButtons` (`pausad`/`avbruten`/`aktiv`, projekt only — `src/components/ProjektStatusButtons.tsx`). Detail-page save payloads deliberately omit `status`; don't add it back. New besiktningar and projekt are inserted with `arende_status: 'vilande'` so Öppna ärende has something to flip.
  - **All three status buttons are hidden from styrelse**, for felanmälan, besiktning *and* projekt alike — styrelse is read-only by spec, and moving an ärende's lifecycle is not theirs. The check is `isStyrelse(profile?.role)` **inside each component**, next to its existing stage check, deliberately not at the call sites: the buttons render on three detail pages plus dag-rapport, and a per-call-site gate is one new surface away from leaking again. Admin and entreprenör keep them (an entreprenör working the ärende is exactly who öppnar/avslutar it — see the note in `permissions.ts:canAccess`).
  - **Every status write verifies that it actually wrote**, via `assertWritten()` (exported from `OppnaArendeButton.tsx`, used by all three buttons). PostgREST does *not* error on an UPDATE that RLS filters away — it matches zero rows and returns success, so the mutation resolved, the success toast fired, and the ärende never moved. That was the observed "Öppna säger att ärendet öppnades men ingenting händer" for styrelse. The writes now `.select("id")` and throw a Swedish behörighet error on an empty result. Keep the `.select()` on any new status write or the silent-success bug comes straight back.
  - Hiding the button is **UI only, not access control** — but RLS *is* already denying the styrelse UPDATE (that's why the write was a no-op rather than a real change). The button gate removes a misleading control; it isn't what protects the data.
  - `property_objects.status` **used to be the one exception (a manual ok/behöver_tillsyn/ur_funktion dropdown) but is not anymore** (changed 2026-08-11) — an objekt's health is now derived the same way, via `deriveObjectStatus` in `src/lib/object-tokens.ts`. It takes the *worst* härledd status among the objektets non-avslutade felanmälningar, besiktningar and projekt (ranked forsenad > bradskande > pagaende > ny; pausad/avbruten/avslutat don't count) and falls back to a green "OK" when none are active. The DB column itself is untouched (still exists, still defaults on insert) but nothing reads or writes it anymore — don't reintroduce a dropdown bound to it. Wired everywhere an objekt's status renders: the objects list (`_authenticated.properties.$id.objects.index.tsx`), the objekt detail header (`_authenticated.properties.$id.objects.$objectId.tsx`, now read-only), and the apartment page's "Kopplade objekt" mini-list (`LinkedObjects` in `_authenticated.apartments.$id.tsx`). Each of those does its own "bara mina ärenden" entreprenör-scoped fetch of the objektets issues/inspections/projects before deriving — don't compute it from an unscoped read or an entreprenör sees the severity of ärenden they otherwise can't see.
  - `apartments.status` and `actions.status` remain not covered, deliberately — physical/tenancy state, not ärendetid. Those keep their dropdowns.
- **Prioritet is derived from the deadline too — no prioritet dropdown exists anywhere inside the portal.** `derivePriority(dueDate, {from, dueLabel})` in `src/lib/issue-tokens.ts` is the single rule: `PRIORITY_THRESHOLDS` is `SLA_DAYS` read backwards (≤1 dygn → akut, ≤2 → hög, ≤5 → normal, beyond → låg), and **no deadline → `normal`, never `lag`** — låg means "ingen tidsgräns alls" and must not be handed to an ärende nobody has taken a position on. Render via `<DerivedPriorityField>` / `<DerivedPriorityBadge>` (`src/components/DerivedPriorityField.tsx`).
  - The frist is measured **from `created_at`** (or today on a creation form), i.e. *how wide a window the ärende was given* — not how close the deadline is now. Time running out is what the derived **status** says (Brådskande/Försenad); prioritet must stay stable or every ärende drifts to akut on its own.
  - Only `issues` has a `priority` column, and it is still written — but never picked. `issues.new`, the `IssuesTab` inline form in `_authenticated.apartments.$id.tsx`, and the `issues/$id` save payload all stamp `derivePriority(deadline).key`, so editing the deadline re-stamps prioritet. Adding a `priority` value from anywhere else re-introduces the contradiction this removed.
  - Besiktning and projekt have no `priority` column and never did; their pages show a read-only derived prioritet off the same tidsgräns their status uses (`derivePriorityFromStatus` + `DerivedStatus.dueDate` — nästa besiktning / intervall, resp. slutdatum). Don't add a column for it.
  - **Exception, deliberate: the public `/felanmalan` survey keeps prioritet as a resident-supplied field.** The boende has no deadline to set but must be able to tell the entreprenör how urgent it is, so `submit-felanmalan` still accepts `priority` (defaulting to `normal`). The form does not currently render a control for it — if one is added, leave it alone; do not "fix" it to match the admin rule.
- **Ansvarig** (`assigned_contact_id` on issues/inspections/projects, FK → `contacts`) — internal-reference-only assignment, no login for contractors. Separate from the older `assigned_to`/`contractor_id` columns which point at `profiles` (internal staff) — don't conflate the two.
- **An entreprenör exists twice: a login (`profiles`) and a pickable name (`contacts`, joined on `contacts.profile_id`).** `<AnsvarigDropdown>` lists the *contacts* side. Deleting the login in Inställningar → Användare calls the `invite-user` Edge Function, which only removes the profile — the contact row survives, so **anything that removes an entreprenör must also retire the contact or the deleted person keeps appearing in every Ansvarig dropdown**. `handleDelete` in `_authenticated.installningar.tsx` does this: it looks up `contacts` by `profile_id` **before** invoking the function (the FK may null the link out as a side effect of the delete), then sets `active = false, profile_id = null` afterwards.
  - **Contacts are retired, never hard-deleted, once assigned.** `contacts.active` (`supabase-functions/contacts-active-flag.sql`) hides a contact from the dropdowns while `assigned_contact_id` keeps pointing at it, so old ärenden still show who was ansvarig. `AnsvarigDropdown` filters `active !== false` **but always keeps the currently-selected contact in the option list** (rendered "— inaktiv") — drop that exception and every ärende assigned to a retired entreprenör silently reads "Ej tilldelad". Admins toggle Status: Aktiv/Inaktiv on `/contacts/:id`.
  - Read paths that touch `active` use `select("*")` on purpose: the column comes from a hand-run migration, and naming it explicitly would 400 every ärende form if the frontend ships before the SQL is applied.
  - The dropdown's cache key is `["contacts-entreprenorer"]` — distinct from the list's `["contacts", …]`. Any contact write must invalidate **both** or the dropdown goes stale.
- **Kontokontinuitet: samma e-post = samma person** (`supabase-functions/account-continuity.sql`, added 2026-07-28). Accounts get deleted and re-invited routinely, and `contacts.profile_id` used to be populated *by hand only* — so a returning entreprenör got a fresh `profiles.id` that matched nothing, and Dag Rapport, the fastighetsgrids and every RLS helper (`has_apartment_assignment`/`has_property_assignment`/`is_my_arende`, all keyed on `contacts.profile_id = auth.uid()`) went silently empty. The link is now maintained by the database, keyed on **normalized e-post (`lower(btrim(email))`)** — the only identifier that survives a delete.
  - `profiles_remember_account()` (BEFORE DELETE on `profiles`) snapshots the account into `account_memory` — linked contact, `styrelse_properties`, `chat_participants` incl. `last_read_at` — then retires the contact. **BEFORE, not AFTER**: those two child tables are `ON DELETE CASCADE`, so after the delete there is nothing left to photograph.
  - `profiles_restore_account()` (AFTER INSERT, and AFTER UPDATE OF role, email) replays it. The **new** role decides: styrelse gets its buildings back, only an entreprenör gets a contact auto-created. The contact link is restored for every role regardless — the post belongs to the person and their old ärenden still point at it.
  - `link_or_create_contact()` is the single linking rule (already-linked → remembered post → same e-post → create). `ensure_my_contact_link()` is the `auth.uid()`-only wrapper the client may call; `link_or_create_contact` takes an arbitrary profile id and is **revoked from `authenticated`** — don't expose it.
  - `useMyContactId` calls that RPC when the `profile_id` lookup comes back empty, so the link self-heals even for accounts created outside the triggers. The old "Ditt konto är inte kopplat till någon kontaktpost"-banner on `EntreprenorDagRapport` is **deliberately deleted** — a comment marks the spot. Don't reinstate it; a missing link is now a bug to fix, not a state to render.
  - Deleting still removes access immediately (the login is gone). `account_memory` holds e-post + rollhistorik and is `REVOKE ALL` from anon/authenticated — only the SECURITY DEFINER functions touch it.
- **Apartment identity**: `(property_id, apartment_number, trappa)` is unique (`apartments_property_number_trappa_uidx`, see `supabase-functions/apartment-trappa-identity.sql`). Apartment numbers repeat across stairwells, so the number alone is **not** an identity. All three parts are required on every apartment write path.
- **Trappa on `apartments` is part of that identity — required, never optional.** The `/felanmalan` public form connects a resident to their unit on exactly this triple, so an apartment saved without a stairwell can never be matched and every submission for it creates a duplicate unit. Both parts are normalized through `normalizeApartmentNumber` / `normalizeTrappa` in `src/lib/apartment-tokens.ts` — **both digits only** (number: leading zeros significant, `0203` ≠ `203`; trappa: letters/spaces/punctuation stripped, a single digit like `1` is valid — changed 2026-08-17, stairwells in this portfolio are identified by number, not letter; the old letters-only rule stripped digits and rejected a numeric trappa as blank). **`normalizeTrappa` is duplicated by hand inside `supabase-functions/submit-felanmalan.ts` and the two must stay byte-identical** — if they drift, admin-created apartments stop matching resident submissions silently.
  - Three admin write paths exist and all three must enforce this: `_authenticated.apartments.new.tsx`, the InfoTab editor in `_authenticated.apartments.$id.tsx`, and the inline form in `ApartmentsTab` (`src/components/property-tabs.tsx`). The last one is easy to miss.
  - **Enforced at the DB level as of 2026-07-27**: `trappa` is `NOT NULL` *and* carries `apartments_trappa_not_blank` (`CHECK (btrim(trappa) <> '')`), applied via `supabase-functions/apartment-trappa-required.sql` — all four steps are run, nothing pending. Blank trappa can no longer be inserted by *any* path, including a bulk import or a hand-written INSERT in the SQL editor. The four writers (three admin forms + `submit-felanmalan`) already rejected it client-side; the constraint is the backstop for write paths that don't exist yet.
  - The empty string was the historical "no stairwell recorded" sentinel (NULL would silently defeat the unique index, since Postgres treats every NULL as distinct). It's now rejected outright. Legacy blank rows render as a red **Saknas** in the Trappa column on the property page — that display path is still worth keeping, but no row should reach it any more.
- **Trappa on `inspections` and `issues`** is a different thing: plain descriptive free text, not a matching key. Don't conflate it with the `apartments.trappa` identity field.
- **Reporter fields** (`reporter_name`, `reporter_phone`, `reporter_email` on `issues`) — required on the public felanmälan form, optional on the internal admin form. `submission_source` = `'admin'` | `'public_form'`.
- **Objekt** (`property_objects`): 8 types (hiss, vind, miljörum, källare, SBA — never abbreviate, tvätt, förråd, lokal), optional `apartment_id` link, härledd status (see above, no longer a manual dropdown and no longer logged to loggbok on change since nothing writes it anymore).

## Public survey → apartment connect-or-create (important, easy to break)
`/felanmalan` (no login) posts to Edge Function `submit-felanmalan` (code lives in `supabase-functions/submit-felanmalan.ts`, deployed manually via Supabase dashboard — **not** part of the Vite build, edit that file and redeploy by hand). Flow:
1. Resident types digits-only `apartment_number` **and `trappa`, both required** (no dropdown — showing one would leak neighbors' apartment numbers).
2. Function (service role, bypasses RLS) looks up `(property_id, apartment_number, trappa)`; creates the apartment if missing (`created_via = 'public_form'`), tagged for admin review.
3. Issue is inserted with `submission_source = 'public_form'`, `apartment_id` resolved above, plus a best-effort loggbok "intake" entry.
Anon RLS read access on `properties` (name only) is required for the property dropdown to populate — see `felanmalan-public-read.sql`. Anon read on `apartments` was deliberately **revoked** (privacy) once the dropdown was removed in favor of type-to-connect.

## Apartment Tidslinje
`/apartments/:id` defaults to a **Tidslinje** tab (`TimelineTab` in `_authenticated.apartments.$id.tsx`) merging issues + inspections + logbook_entries into one chronological feed. This is the "apartment profile" / activity history view — check here first for anything about an apartment's history rather than re-deriving it from the three tables separately.

## Historik / `audit_events` — "vem gjorde vad, när"
Separate from Tidslinje: a per-apartment **audit trail** rendered at the bottom of the **Info** view (below Spara), not as a tab — `ApartmentAuditTimeline` (`src/components/ApartmentAuditTimeline.tsx`), read-side helpers in `src/lib/audit.ts`. Covers issues + inspections + apartments; **projekt are building-level only because `projects` has no `apartment_id` column**, so their rows land with `apartment_id = NULL`.

- **Written entirely by database triggers**, never by client code — `supabase-functions/audit-events-triggers.sql` (`audit_log_changes()` on issues/inspections/projects/apartments). `src/lib/audit.ts` contains no writer. Don't add client-side audit calls; the triggers already cover every path including the `submit-felanmalan` Edge Function.
  - Each trigger takes an **explicit column allowlist**. This is load-bearing: all three ärende detail pages fire `update({viewed_at})` on mount, so without it merely opening a page would write an audit row. `viewed_at`/`updated_at` must never be added to an allowlist. Adding a genuinely auditable column means editing the allowlist *and* `FIELD_LABEL` in `src/lib/audit.ts`.
  - The whole trigger body is wrapped in `EXCEPTION WHEN OTHERS` — an audit failure degrades to no-logging and must never abort a user's save.
  - `lifecycle_of()` in SQL **mirrors `LIFECYCLE_OF`** in `src/lib/issue-tokens.ts`; same byte-for-byte contract as `normalizeTrappa` ↔ `submit-felanmalan.ts`. It also papers over the existing split where `OppnaArendeButton` writes `status = 'oppet'` (not an `issue_status` enum member) while `dag-rapport` writes `'pagande'`.
- **Rows are self-contained; the read path joins nothing.** Actor name/company/role are snapshotted at INSERT by the SECURITY DEFINER trigger `audit_events_stamp_actor()` from `auth.uid()`. **Never add a `profiles:actor_profile_id(...)` join** — `chat.sql`'s `profiles_select_for_chat` hides other users' profiles from styrelse/entreprenör, so the join returns `null` for exactly the cross-role attribution this feature exists to provide. FK values in `old_value`/`new_value` are likewise pre-resolved to names by `audit_label()`; raw ids live in `meta`.
- **Append-only, not immutable** (changed 2026-07-27 — `admin-delete.sql`). INSERT and UPDATE stay revoked for `authenticated`, so a row still cannot be fabricated or rewritten from the client and an entry that exists is trustworthy. But admin now has a DELETE policy: the client required that Historik be clearable, selected rows or all of it. The log is therefore no longer guaranteed *complete*. Deletion goes through the same multi-select toolbar as loggbok — see **Radering** below.
- **Visibility** (`audit_events_select`): admin all; styrelse via `styrelse_properties`; entreprenör via `has_apartment_assignment()` — **one assignment grants the whole apartment's history**, a deliberate product decision — plus `is_my_arende()` for projekt/building-level ärenden. All membership tests go through SECURITY DEFINER helpers to avoid Postgres 42P17 recursion, following the `chat.sql` pattern.
- **⚠ NOT APPLIED to the live DB as of 2026-07-27.** Proven, not guessed: `entreprenor-read-scope.sql`'s preflight returned `has_apartment_assignment_fn = false`, and running SQL that called the function failed with `42883 function has_apartment_assignment(uuid) does not exist`. So the whole Historik/`audit_events` feature described in this section is **code without a database behind it** — the reads degrade to empty, nothing is being logged. Everything below describes the intended design, not the current state. `entreprenor-read-scope.sql` therefore defines `has_apartment_assignment()` **itself** (verbatim copy, `CREATE OR REPLACE`, either run order is safe) — **that copy and the one in `audit-events.sql` must stay byte-identical**, same contract as `normalizeTrappa` ↔ `submit-felanmalan.ts`.
- Run order, all by hand: `audit-events.sql` → `audit-events-triggers.sql` → `audit-events-backfill.sql`. The backfill seeds felanmälan lifecycle from `issue_status_history` (which until now was written by three places and read by none). Besiktning/projekt lifecycle and all field edits are **not** recoverable — no historical record ever existed.

## Roles on apartment pages
`/apartments` is reachable by **all three roles**, but scoped differently: admin everything; styrelse their `styrelse_properties` buildings; entreprenör only apartments where they hold an ärende assignment (`useMyAssignedApartmentIds`, mirroring the `has_apartment_assignment()` RLS helper — change both together). `ApartmentsTab` filters its roster the same way.
**`InfoTab` is read-only for everyone except admin** — the form body is wrapped in a single `<fieldset disabled>` (so fields added later inherit the gate automatically) and the Spara/Radera row is replaced by a note. Before this, styrelse — read-only by spec — could edit and delete apartments.

## "Bara mina ärenden" — `useMyArendeScope`, and the surfaces that forgot it
Client spec (2026-07-30): **an entreprenör sees every ärende assigned to them, whatever its status, and nothing else.** Their own avslutade ärenden stay visible (that's their record of work done); other people's ärenden never appear, finished or not. This replaced the earlier "one assignment grants the whole apartment's history" decision — that rule now applies to `audit_events` only.

`useMyArendeScope()` (`src/hooks/useMyContactId.ts`) is the one implementation: `filterContactId` is `null` for admin/styrelse (no narrowing) and the linked contact id — or `"__none__"`, matching nothing — for an entreprenör. Apply it to **every** ärende read that isn't already keyed on assignment, and gate the query on its `ready` flag (an unscoped first fetch flashes everyone's data before the contact link resolves):

```ts
const { filterContactId, ready } = useMyArendeScope();
useQuery({ queryKey: [..., filterContactId], enabled: ready, queryFn: async () => {
  let q = supabase.from("issues").select(...).eq("apartment_id", id);
  if (filterContactId) q = q.eq("assigned_contact_id", filterContactId);
```

Wired: the apartment **Tidslinje**, felanmälnings- and besiktningstabellerna (`_authenticated.apartments.$id.tsx`), the akut-klockan incl. its realtime toast (`AkutWatcher.tsx`), `GlobalSearch` (issues + projects), and the **byggnadskortens siffror** (`SectionOverviewPage.loadStats`, `IssuesPropertyOverview.loadOpenIssueBadges`, `OppnaArendenOverview.loadCombinedOppnaStats`). The property-scoped `IssuesTab`/`InspectionsTab`/`ProjectsTab` in `property-tabs.tsx` already did this inline with the same `?? "__none__"` pattern.

- **Counts are part of the scope, not decoration.** A card that said "Felanmälan — 12" over a list containing 1 both contradicted the page and leaked how much other work the building has.
- **It is UI filtering, not a boundary** — the DB still lets any authenticated user read every ärende (closing that needs RLS on issues/inspections/projects; deferred by decision 2026-07-30). Never describe this as access control.
- Known remaining leak, deliberate for now: **loggbok**. `logbook_entries` has no ärende link, and lifecycle writes put the ärende's title in the entry text, so an entreprenör can still read loggbok lines about other people's ärenden. Fixing it needs a column on `logbook_entries`, not a filter.
- If an entreprenör sees *nothing* rather than too much, it is usually not this code: `contacts.profile_id` is filled in **by hand**, so an ärende assigned to an unlinked duplicate contact is invisible everywhere. `supabase-functions/diagnose-entreprenor-scope.sql` (read-only) prints `syns_for_inloggning` per ärende and is the fastest way to tell the two apart.

## Dag Rapport — three different pages on one URL
`/dag-rapport` branches on role in `_authenticated.dag-rapport.tsx`: admin keeps the building-wide day view (`VeckansArendenSection` + today's akuta/förfallna felanmälningar), **entreprenör gets `EntreprenorDagRapport`** (`src/components/EntreprenorDagRapport.tsx`) — their landing page (`HOME_FOR_ROLE`) and whole working surface. Two lists, both fed by `useMyArenden` (`src/hooks/useMyArenden.ts`):
1. **Öppna ärenden** — `lifecycle === 'oppet'`, i.e. what they have started. Row → BottomSheet → `AvslutaArendeButton`.
2. **Alla ärenden** — every non-avslutat assignment, ordered by tidsgräns (`derived.dueDate`) with prioritet as tie-break, deadline rendered as veckodag + datum. Row → BottomSheet → `OppnaArendeButton` when still vilande.

**The sheet's action row is exactly the livscykel and nothing else:** vilande → `[Öppna ärende] [Avsluta ärende]`, oppet → `[Avsluta ärende]`. The second vilande-button is `<AvslutaArendeButton allowVilande>` — the one-click close for an ärende that didn't need doing; it carries the same "Avsluta ärende" label as the oppet-stage one on purpose, since it is the same action with the same outcome. Navigation to the full ärendesida is a **text link ("Visa hela ärendet") up in the sheet header**, deliberately not a button: sitting next to Öppna it read as a second open-button and that was the bug this replaced. The far-right dismiss says **Tillbaka**, not "Stäng". Don't put a fourth control back in that row.

Section 1 is deliberately a subset of section 2. Avslutade ärenden appear in neither — those belong to the not-yet-built `/avslutat`.

**Styrelse gets `StyrelseDagRapport`** (same file, added 2026-07-29) — the identical worklist for the buildings they're attached to, read-only. They neither order the work nor perform it, but "what is going to be done in my building, by whom, and when" is exactly their question. Layout, sorting, härledd status and the sheet are shared with the entreprenör view via `DagRapportView`; only two things differ.
- **The data source is a different question, not a wider one.** `useByggnadensArenden` (same file as `useMyArenden`) filters on `property_id IN useVisibleProperties()` — "what is happening in my houses". `useMyArenden` filters on `assigned_contact_id` — "what is assigned to me". `loadArenden(scope)` serves both off one `ArendeScope` union; **never collapse the two**, or an entreprenör starts seeing the building's other ärenden. Separate cache prefix (`["byggnadens-arenden", …]`) so a lifecycle write doesn't needlessly invalidate the styrelse view.
- **`readOnly` means the lifecycle row is never rendered** — not disabled, not CSS-hidden. Styrelse must not even see that Öppna/Avsluta exist. Second layer: the buttons already hide themselves from styrelse internally, so removing one guard doesn't leak.
- `assignedName` on `MyArende` (resolved via a separate `contacts` lookup, same no-embed reasoning as the apartment label) is shown in every styrelse row and first in the sheet's meta — it's the column they actually came for. `showAssignee` is off for the entreprenör, where it would just repeat their own name.
- `noProperties` distinguishes "no buildings attached to this account" from "nothing scheduled", and renders a notice instead of a misleading empty list.

**Sidebar statusprickar (entreprenör only)** — `useMyArendeDots` (`src/hooks/useMyArendeDots.ts`) puts a dot on the Felanmälningar / Besiktningar / Projekt nav items when the signed-in entreprenör has non-avslutade ärenden of that type assigned. It reads `useMyArenden` and nothing else, so the dot can never promise work the page then doesn't list; widening it building-wide would break that. Rendered by `NavDot` in `AppShell` (full, mobile-overlay and mini sidebars) around the existing `<StatusDot>` — the same dot as the fastighetskort and sektionsknappar, so colour and pulsering keep meaning one thing app-wide; härledd status only feeds the tooltip text. Admin/styrelse get an empty map and no extra query (`useMyContactId` only resolves for entreprenör).

- **`useMyArenden` is the only definition of "my ärenden": `assigned_contact_id = ` the contact linked to the login (`useMyContactId`).** Never widen it to building scope — an entreprenör working in a building must not see that building's other ärenden. It normalizes the three tables' disagreeing columns (`status` vs `arende_status`, `deadline` vs `next_due_date` vs `end_date`) into one `MyArende` shape and computes härledd status on render, not in the query cache, so a tab left open overnight doesn't keep yesterday's "Brådskande".
- The page writes no status itself. `OppnaArendeButton`/`AvslutaArendeButton` do, and both now export `canOppnaArende`/`canAvslutaArende` (so a list can tell whether a row has any action left before rendering an action bar) plus an `onDone` callback (so the host sheet can close itself). Both invalidate the `["mina-arenden"]` prefix.
- The inspections read uses `select("*, properties(name)")` **on purpose**: `inspections.trappa` from `trappa-field.sql` is **not applied to the live DB** (verified 2026-07-27 — `42703`), so naming it explicitly 400s the whole query. `issues.trappa` does exist.
- Apartment identity (`Lgh 1203 · Trappa B`) comes from a **separate `apartments` lookup keyed on the collected `apartment_id`s**, not a PostgREST embed — an embed needs a declared FK on both `issues` and `inspections`, and a missing one takes the entire page down instead of just the lägenhetslabel.
- The sheet's **"Öppna ärendet"** goes through the fastighet (`/properties/:pid/<section>/:id`), falling back to the flat `/issues/:id` only when the ärende has no `property_id`. Fastighet först is the navigation model everywhere; the sheet must not shortcut past it.

## Fastighet först — the building grids, and how they went blank
`/fastigheter`, `/issues`, `/inspections`, `/projects`, `/apartments`, `/loggbok` are **building pickers**: a grid of fastighetskort, click one, then the section list inside that building. This ordering is a product requirement, not an implementation detail — do not "simplify" any of them into a flat ärendelista.

- All of them go through **`useScopedProperties(columns)`** (`src/hooks/useVisibleProperties.ts`), which asks the database for *exactly* the allowed buildings (`.in("id", …)`) instead of fetching every building and discarding the rest. Admin (`allowedIds === null`) still queries all. The per-page client-side `allowedIds` filter is kept as a cheap second check. Its cache key must stay prefixed `["properties", …]` — existing writers invalidate on that prefix.
- **Entitlement never came from the grid; it comes from `useVisibleProperties`** (styrelse → `styrelse_properties`, entreprenör → the buildings their assigned ärenden live in). That half always worked.
- **The bug this replaced (2026-07-27):** step one — "give me the buildings" — returned nothing for an entreprenör, because `properties` had no SELECT policy covering them. Correct filter over an empty list = *"Inga fastigheter hittades"* on all four pages, while Dag Rapport worked because it is the only view that never reads `properties`. Fixed DB-side by `supabase-functions/entreprenor-read-scope.sql`: `has_property_assignment()` (SECURITY DEFINER, mirrors `has_apartment_assignment()`/`is_my_arende()`, and **includes projekt** since a building-level projekt must still open its building) plus SELECT policies on `properties` and `apartments`. Permissive policies OR together, so it only widens for a login whose `contacts.profile_id` matches — admin/styrelse/anon rules untouched. `useVisibleProperties` and `has_property_assignment()` are the same rule in two languages; change both together.
- Symptom to recognise next time a role sees an empty grid: **check whether that table has a read policy for the role at all** before touching the page. A missing policy returns `[]` with a 200, so it looks exactly like "no data".

## `useRecordScopeGuard` — three states, not two
`src/hooks/useRecordScopeGuard.ts` guards every detail page (they're all URL-reachable). `assignedContactId` and `propertyId` each carry **three** meanings and collapsing them is a real bug:
- a string → known, compare it; `null` → genuinely unassigned/no building, deny a non-admin; **`undefined` → not known yet (loading, or the read failed) → decide nothing.**
- Call sites must write `data ? (data.assigned_contact_id ?? null) : undefined`, **never** `data?.assigned_contact_id ?? null`. The `??` form turned a failed read into "assigned to nobody" and evicted an entreprenör from their own felanmälan.
- Denial redirects to the role's own home (`homeForRole` in `src/lib/permissions.ts`, shared with `_authenticated.tsx`'s `beforeLoad`), not to a section grid. Bouncing an entreprenör onto a building picker they can't populate is what read as "the app lost my ärende".

## Edge Functions (NOT in this repo's build — deployed by hand)
Source kept in `supabase-functions/*.ts` for reference/version-tracking only; Supabase doesn't read from this folder. After editing, the file must be manually copied into the Supabase dashboard and redeployed.
- `invite-user` — creates an auth user + profile (source not kept locally, only referenced in chat history)
- `submit-felanmalan` — public felanmälan intake, see above
Both need a service role key. Supabase reserves the `SUPABASE_` prefix so you **cannot create** `SUPABASE_SERVICE_ROLE_KEY` yourself — but the platform auto-injects it into every function as a "default secret" (visible under Edge Functions → Secrets → Default secrets, marked deprecated but still working). A custom secret named exactly `SERVICE_ROLE_KEY` also works. `submit-felanmalan` reads `SERVICE_ROLE_KEY` and falls back to `SUPABASE_SERVICE_ROLE_KEY`, returning a 500 with an explicit Swedish message if neither resolves — this had already broken the function twice (missing secret, then name/value swapped in the dashboard form). If `invite-user` returns a non-2xx, check its secret first; it has no such fallback.

## Notiser (top-bar bell)
`NotificationsProvider` (`src/lib/notifications.tsx`, wraps `AppShell` in `_authenticated.tsx`) watches `chat_messages` INSERTs globally over Realtime — no filter, because RLS already limits the stream to conversations you're in (membership is re-checked client-side anyway). It feeds two consumers in `src/components/NotificationCenter.tsx`: `NotificationBell` (dropdown panel, also lists open akut-ärenden via `useAkutIssues` from `AkutWatcher.tsx`) and `NotificationToasts` (slide-down popups under the top bar, `TOAST_MS = 1000`, dismissed by scroll/swipe up).
**There is no notifications table.** Read state is derived from `chat_participants.last_read_at`, so opening a thread in `/chatt` clears the badge and "Markera alla som lästa" is just an UPDATE on your own participant rows. Don't add a `read` flag without deciding which side wins.

## Radering (admin) — cascade + multi-select loggbok
Admin-only everywhere, on both sides: every UI entry point renders `null` for other roles, and every DELETE policy in `supabase-functions/admin-delete.sql` is gated on `is_admin()`. Styrelse is read-only by spec; an entreprenör must never be able to erase an ärende they were assigned.

**`supabase-functions/admin-delete.sql` must be run for any of this to work** (by hand, like the rest of `supabase-functions/*.sql`; safe to re-run). Before it, `<DeleteButton>` failed two ways: FK 23503 on any fastighet with history, and — worse — a silent no-op where RLS had no DELETE policy, `.delete()` removed zero rows and PostgREST returned 200 so the UI reported success over an untouched list. **Both client helpers now `.select("id")` after every delete and throw if the row count is short**; don't drop that, it's the only thing that distinguishes "deleted" from "refused".

- **Cascade** (client decision, 2026-07-27): deleting a fastighet deletes its lägenheter, ärenden, objekt, dokument, loggbok och åtgärder; deleting a lägenhet deletes its ärenden och loggbok. Implemented as a **sweep** in the SQL, not hand-written ALTERs — the Lovable-generated constraint names aren't predictable, so a DO block rewrites every single-column FK pointing at `properties`/`apartments`/`issues`/`inspections`/`projects`/`property_objects`/`logbook_entries`. Five exceptions are `SET NULL` (`contacts.property_id`, `property_objects.apartment_id`, `*.property_object_id`) because the child outlives the parent. `CASCADE_CHILDREN` in `src/components/DeleteButton.tsx` mirrors the sweep to count and name the children in the confirm dialog — **add a table in one place and you must add it in the other**, or the dialog under-reports what disappears.
- The SQL **never runs `ENABLE ROW LEVEL SECURITY`**. A table with RLS off today is protected by grants alone; switching it on while adding only a DELETE policy would deny SELECT/INSERT/UPDATE to everyone and take the app down. The loop adds a policy only where RLS is already on.
- Storage is not handled: cascading `documents`/`issue_images`/`project_images` deletes the pointers, not the bucket objects.

**Multi-select delete — `src/components/LogSelection.tsx`, one mechanism for all seven log surfaces.** File-explorer interaction: checkbox per row, Välj alla / Avmarkera alla, one `Radera valda (N)` button. **Hard delete, no tombstone** — deliberately *not* the chat behaviour (`chat-message-delete.sql` leaves "Meddelandet togs bort"); here the row is gone and nothing marks that it existed.
- A row is a `{table, id}` `LogTarget`, not a display object, so a merged timeline can mix loggboksposter with the besiktning/projekt/felanmälan rows its events are *derived* from. Selecting such an event and deleting it **deletes the ärende itself** — `LogSelectionBar` spells that out in the confirm dialog ("raderas i sin helhet — inte bara raden i loggboken").
- Selection is stored as keys and the target list is re-derived from the visible rows each render, so filtering or deleting prunes it automatically and "Välj alla" can never reach a row that's off-screen behind a filter chip.
- `LogSelectCheckbox` takes an array when one card stands for several rows — a Historik card is one save, i.e. one `audit_events` row per changed field.
- **`deleteLogTargets` purges the deleted ärende's `audit_events` afterwards.** It has to: `audit_log_changes()` fires on DELETE and writes a "Tog bort felanmälan" row, so without the purge, clearing an event from the loggbok would make it reappear under Historik. It also cleans `logbook_comments` rows keyed by the synthetic `event_key` (`i-<id>`/`p-<id>`), which are foreign-keyed to nothing and no cascade can reach.
- `<DeleteButton>` on a detail page deliberately does **not** purge audit — deleting an ärende from its own page is an ordinary admin action and stays on record. "Clear the log" is a different intent from "delete this thing".
- Wired surfaces: fastighetens loggbok (`PropertyLoggbokWithComments`), alla byggnaders loggbok (`AllBuildingsLoggbok`, the "Alla byggnader" tab on `/loggbok`), lägenhetens Loggbok-flik och Tidslinje, objektloggen on both objekt pages (via the optional `selection` prop on `LogbookEntryCard`), Historik (`ApartmentAuditTimeline`), and the per-fastighet `property_history` table (`HistoryTab`). Add a new one the same way; don't hand-roll a second selection implementation.

## Loggbok-filtrering — `LoggbokFilterBar`, one bar for all five lists
`src/components/LoggbokFilterBar.tsx` is the only filter UI any loggbok list may use — same reasoning as `LogSelection`: five surfaces (`AllBuildingsLoggbok`, `PropertyLoggbokWithComments`, the Objekt-sidans Loggbok-flik, objektets egen logg, lägenhetens `LogbookTab`) previously each sorted newest-first with no controls, in three different implementations. `useLoggbokFilter(rows, meta)` does the filtering and sorting; the component renders the controls. A surface projects its own row shape into `LoggbokRowMeta` and renders `<LoggbokFilterBar filters={filters} />` — don't hand-roll a sixth.

- **One row of identically-shaped 34px fields**, in order: **Sök** (leads, takes the leftover width) · **Källa** (passed only by the two surfaces that actually mix loggbok/besiktning/projekt rows — the other three would show one permanently-selected option) · **Åtgärd** · **Vem** · **Ordning** (Senaste/Äldst) · **Rensa** (only while filtered). The first version stacked four labelled rows of solid dark chips and read as a wall — three visual languages four rows deep, above the delete toolbar. Two things fixed it without dropping an axis: each control **names its own axis in its resting option** ("Alla åtgärder"), so the uppercase KÄLLA/ÅTGÄRD/VEM/ORDNING labels are gone; and a dropdown is one line whatever the option count, so twelve åtgärder can't wrap into further unlabelled chip rows. Engaged state is the light green tint (`#F0F7EE` + `#5CB84A` border), **not** a solid dark fill. Any control whose option list would have a single entry renders nothing, so a quiet building shows two fields rather than five dead ones. Don't reintroduce chip rows here.
- **No status filter, deliberately.** A loggbokspost records something that already happened; it has no härledd ärendestatus of its own and a status chip here would invite reading it as one.
- **Facets exclude their own axis.** Åtgärd is built from the rows surviving Källa+Sök+Vem, not from the fully filtered set — deriving them from the final result collapses the chip row to the single chip just pressed, which reads as if the other kinds stopped existing. The currently-selected value is always kept in its own list (same exception as `AnsvarigDropdown` keeping a retired contact) or an active filter goes invisible. A group with ≤1 option renders nothing.
- **`actionKindOf(event_type, content)`** (`src/lib/logbook.ts`) is the åtgärdsnyckel. For every event_type but `arende_status_andring` the key *is* the event_type. Status changes split into `oppnad/avslutad/aterupptagen/pausad/avbruten` by parsing the trailing `→ X)` out of the entry text — `OppnaArendeButton`, `AvslutaArendeButton`, `ProjektStatusButtons` and dag-rapport all write `"<titel> (<från> → <till>)"`, and OppnaArendeButton's resume variant puts the status that matters last for exactly this reason. **That text format is a contract now**; changing it silently degrades the filter. Unparseable or unmapped (dag-rapport writes raw `issue_status` values) falls back to the raw event_type — never throws, never drops a row. `ACTION_KIND_LABEL` extends `EVENT_LABEL`; `LogbookEntryCard` and lägenhetens loggbokskort render the same label the chip does.
- **Vem comes from `created_by`, resolved by a separate `profiles` read, not a `profiles:created_by(full_name)` embed**, in `AllBuildingsLoggbok` and `useMergedPropertyTimeline`. An embed needs a declared FK on `inspections`/`projects` too and a missing one 400s the whole feed instead of just losing a name (same reasoning as the lägenhetslabel in `useMyArenden`). Non-admins can only read some profiles (`chat.sql`'s `profiles_select_for_chat`), so unresolved ones fall back to "Okänd" — as would the embed. Rows with `created_by = null` get an explicit **Okänd** bucket rather than being excluded.
- Queries that had to grow a column for this: `logbook_entries` gained `event_type` in `AllBuildingsLoggbok`, `useMergedPropertyTimeline` and lägenhetens `LogbookTab`; `created_by` was added to the logbook/inspections/projects reads in the first two. `TimelineEvent` now carries `event_type`/`actionKind`/`actorId`/`actorName`.
- Empty state goes through `loggbokEmptyText(active, base)` — "Inga poster för det här valet" when filtered, the surface's own wording otherwise. A filtered-empty list must never read as an empty building.

## Form overflow ("textboxes outside their container")
Recurring bug: forms are CSS grids of `auto`/`1fr` tracks holding `<select>`s whose widest `<option>` (long prioritet labels, kategori names, fastighetsnamn) is wider than the card. An auto/1fr track's minimum is min-content, so that option inflates the track past the card and every field in the column spills out the right edge — clipped, because `<main>` sets `overflow-x: hidden`. `src/styles.css` now carries a global net under `.bayt-app` (`min-width: 0` on form wrappers, `box-sizing`/`max-width` on controls). Inline styles still win, so a field that needs a real floor keeps it. Note the net only covers routes inside `AppShell` — public routes (`/felanmalan`, `/login`, `/start`) are outside `.bayt-app` and rely on their own inline `minWidth: 0`.
